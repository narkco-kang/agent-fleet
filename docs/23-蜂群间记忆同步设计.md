# AgentFleet 蜂群间记忆同步 · 开发设计文档

> 面向软件开发团队。目标：把「蜂群间（多设备）记忆同步」从「代码已写但未接通」变为「真正跑起来的分布式记忆账本」。
> 前置结论（已核实代码）：memory workspace 已实现完整的同步（gossip/catchup）与共识（fork/producer），但 backend 集成层只用了「单机 leader 出块 + 签名 + 落盘 + BM25 检索」，gossip/catchup/fork 在 backend 与 device-agent 中**零引用**。

---

## 1. 背景与目标

### 1.1 为什么做

AgentFleet 的定位是「多设备蜂群协同」。每台设备各自执行任务，但它们共享同一个团队目标，需要一份**跨设备一致的团队记忆**——某台设备做过什么、得出什么结论、踩过什么坑，其他设备应该能检索到、能复用。

当前记忆账本（`backend/src/services/memoryLedger.ts`）只实现了：
- backend 作为**单机固定 leader** 出块、Ed25519 签名、落盘、BM25 检索

**没有实现**：
- 区块在设备之间的广播同步（gossip）
- 设备落后时的补同步（catchup）
- 多写入方时的分叉解决（fork）

也就是说，现在只有 backend 一台机器记账，**设备之间没有「记忆同步」**——这正是区块链式账本本应发挥价值、却还没接线的地方。

### 1.2 目标

让「team 账本」成为真正跨设备的同步账本：
- backend 出块后，区块自动广播到所有在线设备
- 设备离线/断线重连后，自动拉取缺失区块补齐
- 所有设备最终收敛到同一份团队记忆（含语义检索索引）

### 1.3 非目标（本期不做）

- 设备作为独立出块方（多 leader）——本期保持「backend 固定 leader」，避免引入完整共识复杂度
- 跨团队（不同 team）的记忆隔离——已由 `LedgerStore` 的 `group` 参数天然支持，本期聚焦 team 层

## 2. 现状盘点

### 2.1 memory workspace 已实现（可直接复用，无需重写）

| 模块 | 文件 | 能力 |
|------|------|------|
| 区块核心 | `memory/src/core/block.ts`、`chain.ts`、`merkle.ts` | 哈希链 + Merkle 树 |
| 加密 | `crypto/hash.ts`、`ed25519.ts`、`canonical.ts` | 确定性哈希 + Ed25519 签名 |
| 共识 | `consensus/mempool.ts`、`producer.ts`、`fork.ts` | 幂等 mempool、固定 leader 出块（`start(onBlock)` 回调）、最长链 + 确定性 tie-break |
| **同步** | `sync/gossip.ts`、`catchup.ts`、`messages.ts` | **GossipNode（广播 + 洪泛去重）、catchUp（拉取 + 逐块验证 + 追加）、8 种同步消息编解码** |
| 存储 | `storage/ledger.ts` | `LedgerStore`（group 隔离 local/team，原子写 + 建议锁） |
| 验证 | `validation/verifier.ts`、`tamper.ts` | `verifyBlock` / `verifyChainSigned` / 篡改检测 |
| 语义检索 | `search/*` | BM25 召回 + secret 脱敏 |

### 2.2 关键接口（接线要用到的）

```ts
// 出块（backend 已用，缺 onBlock 广播回调）
producer.start(onBlock?: (block: Block) => void | Promise<void>): () => void;

// gossip 广播（需注入 relay 回调）
class GossipNode {
  constructor(relay: RelayFn, selfId: string);
  broadcastBlock(block: Block, peers: string[]): Promise<string[]>;
}
type RelayFn = (to: string, message: Envelope) => void | Promise<void>;

// 补同步（需注入 fetch + onReject）
catchUp(selfTip, peerTip, fetch, ledger, trustStore, onReject?): Promise<CatchUpResult>;

// 消息编解码（8 种，见 memory/src/types/protocol.ts）
encodeBlockBroadcast / encodeBlockRequest / encodeBlockResponse / encodeChainSummary / ...
```

### 2.3 通信链路（gossip 走的通道）

当前架构是** backend 中心化**，设备不直接互通，所有消息经 backend 中转：

```
device-agent ──出站直连──▶ backend /ws        （coordinatorClient）
device-agent ──中继──────▶ backend relayServer （relayClient）
backend ──mDNS 反向──────▶ device-agent lanServer （lanDiscovery）
```

关键通道能力：
- `wsServer.sendToDevice(deviceId, envelope)`：backend 发给指定设备（直连 socket 或 relay 转发），**已有**
- 设备 → backend：走 `handleEnvelope` 的 `switch(type)`，**需要新增 memory.* 分支**

**结论**：gossip 不新建通道，复用现有 `sendToDevice`（backend → 设备）和 `handleEnvelope`（设备 → backend）。这是「中心广播」模型，不是 P2P。

## 3. 架构设计

### 3.1 同步模型：backend 固定 leader + 中心广播，设备只读 follower

```
                    ┌─────────────────────────┐
                    │   backend（固定 leader） │
                    │  - 出块（BlockProducer） │
                    │  - 广播新区块给所有设备  │
                    │  - 应答设备的补同步请求  │
                    └───────────┬─────────────┘
                                │ memory.block_broadcast（广播）
                ┌───────────────┼───────────────┐
                ▼               ▼               ▼
        ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
        │  device-0    │ │  device-1    │ │  device-N    │  ← follower
        │  本地 team 账本│ │  本地 team 账本│ │  本地 team 账本│
        │  接收+验证+追加│ │  接收+验证+追加│ │  接收+验证+追加│
        └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
               └──────── memory.chain_summary（上报链头，触发补同步）────────┘
```

- **backend**：唯一写入方（出块 + 签名），同时是同步源（广播 + 应答）。
- **device-agent**：只读追加（不自己出块），接收广播、补同步。
- 每台设备在本地维护一份 `group="team"` 的 `LedgerStore`，通过同步收敛到与 backend 一致的链。

### 3.2 为什么不用 P2P gossip

- 现有拓扑是星形（设备都连 backend），设备间没有直连通道，P2P 要额外打通设备间通信，成本高。
- 「backend 中心广播」等价于 gossip 的星形退化，用 `sendToDevice` 遍历所有在线设备即可，天然去重（backend 每块只发一次）。
- 保留 `GossipNode` 的接口（`RelayFn`）做抽象，未来若需要设备间直连，只需替换 relay 实现。

### 3.3 消息路由（复用现有 Envelope，type 点分小写）

新增消息类型（进 shared 的 `MessageType`）：

| 类型 | 方向 | 用途 | payload |
|------|------|------|---------|
| `memory.block_broadcast` | backend → device | 广播新区块 | `{ block }` |
| `memory.chain_summary` | device → backend | 上报己方链头，请求补同步 | `{ summary: {tip_index, tip_hash, group} }` |
| `memory.block_response` | backend → device | 返回缺失区块 | `{ blocks }` |
| `memory.block_request` | device → backend | 主动拉取 `[from, to]` 区块 | `{ from_index, to_index? }` |
| `memory.block_reject` | device → backend | 拒收非法块（篡改检测） | `{ index, hash, reason }` |

（`memory.proof_request/proof_response` 本期不做，Merkle 证明留到需要「轻客户端验证单条记录」时再启用。）

## 4. 数据流（4 个场景）

### 场景 A：出块广播（backend → 所有设备）

1. 任务终态 → `memoryLedger.recordTaskTerminal()` → mempool.add + flush() 出块。
2. 出块成功 → 触发广播：遍历 `deviceRegistry.onlineIds()`，对每台设备 `sendToDevice(id, memory.block_broadcast)`。
3. 设备收到 → `verifyBlock`（验哈希链 + 验签名）→ `ledger.appendBlock` → 同步更新本地 BM25 检索索引。

### 场景 B：设备上线补同步（设备落后 → catchup）

1. 设备启动/重连后，发 `memory.chain_summary`（携带本地链头 tip）。
2. backend 收到 → 比对：若设备 `tip_index < backend.tip_index`，回 `memory.block_response`（缺失区块 `[tip+1, ...]`）。
3. 设备收到 → `catchUp()` 逐块验证 + 追加，直到收敛到 backend 链头。

### 场景 C：断线期间 backend 继续出块（块序号不连续）

1. 设备离线，backend 继续出块（index 前进）。
2. 设备重连后补同步（场景 B），因为 `appendBlock` 只接受 `index == tip+1`，缺失会返回 `stale`，此时走 catchup 拉齐。

### 场景 D：分叉（本期保持单 leader，理论上不发生）

- 单 leader 下，只有「设备本地账本与 backend 账本短暂不一致」会出现分叉候选。
- 设备补同步时若发现分歧，用 `chooseMainChain`（最长链 + 字典序 tie-break）选主链，丢弃孤儿分支（不删数据）。

### 5.1 shared（协议层）

### 5.2 backend（leader + 同步源）

**`backend/src/services/memoryLedger.ts`**：
- `flush()` / `recordTaskTerminal()` 出块成功后，回调广播（新增 `onBlock` 回调注入）。
- 新增 `handleChainSummary(deviceId, summary)`：比对链头，落后则回 `block_response`。
- 新增 `handleBlockRequest(deviceId, from, to)`：按区间返回区块。

**`backend/src/services/memorySync.ts`（新文件）**：装配层，负责
- 注入广播回调：出块 → 遍历在线设备 → `sendToDevice`
- 处理设备上行的 `memory.*` 消息 → 调 memoryLedger 的 handler
- 维护 `GossipNode`（若后续要设备间转发，接口已就绪）

**`backend/src/transport/wsServer.ts`**：`handleEnvelope` 的 switch 加 `memory.*` 分支，转交 `memorySync` 处理（复用现有 `taskBridge` 类似注入方式）。

### 5.3 device-agent（follower + 只读账本）

**`device-agent/package.json`**：dependencies 加 `"@agentfleet/memory": "0.1.0"`。

**`device-agent/src/memory/memoryClient.ts`（新文件）**：
- 初始化本地 `LedgerStore(dir, 'team')` + `TrustStore`（信任 coordinator 公钥，公钥经注册/配置下发）
- `onBlockBroadcast(block)`：verifyBlock + appendBlock + 更新本地检索索引
- `onBlockResponse(blocks)`：catchUp 逐块追加
- `syncToCoordinator()`：启动/重连时发 `chain_summary` 请求补同步

**`device-agent/src/messageHandler.ts`**：`handleEnvelope` 的 switch 加 `memory.*` 分支，转交 memoryClient。

**`device-agent/src/coordinatorClient.ts` / `lanServer.ts` / `relayClient.ts`**：连接建立后（open 回调），触发一次 `memoryClient.syncToCoordinator()`。

## 6. 实现步骤（分阶段）

### P0 —— 最小闭环（广播 + 追加，验证同步通路）

1. shared 加 memory.* 消息类型。
2. backend：出块后广播给所有在线设备。
3. device-agent：加 memory 依赖 + 本地账本 + 接收广播追加。
4. **验收**：起 1 backend + 2 设备，backend 记一条任务终态 → 两台设备本地账本都出现新区块、`tip` 一致。

### P1 —— 补同步（断线重连不丢）

1. device-agent：启动/重连发 `chain_summary`。
2. backend：比对链头，回 `block_response`。
3. device-agent：catchUp 追加。
4. **验收**：设备离线期间 backend 出 3 个块，设备重连后自动拉齐到同一链头。

### P2 —— 健壮性（可选）

1. `block_reject` 拒收非法块 + 告警落点。
2. 语义检索索引随同步更新（设备本地也能搜到同步来的记忆）。
3. 单测 + 集成测试（`memory` workspace 已有 test 骨架，补跨进程同步集成测试）。

## 7. 验收标准

| # | 场景 | 预期 |
|---|------|------|
| 1 | 出块广播 | backend 出块后，所有在线设备本地账本 `tip.index`/`tip.hash` 与 backend 一致 |
| 2 | 补同步 | 设备离线 N 个块后重连，自动追平到同一链头，无缺块 |
| 3 | 篡改拒绝 | 设备收到非法块（改 hash/签名）→ `block_reject`，不追加，本地链不变 |
| 4 | 检索一致性 | 设备本地能检索到「从 backend 同步来的记忆」 |
| 5 | 回归 | backend 137 测试 + memory 88 测试全绿 |

## 8. 风险与边界

1. **单 leader 单点**：backend 挂了，团队账本停止出块（设备只读不写）。本期接受此约束，多 leader 需要完整共识（fork 已实现，但写入方协调、防双花需另设计），作为后续演进。
2. **trustStore 公钥下发**：设备验签需要 coordinator 公钥。当前 backend 每次启动 `generateKeyPair()` 生成新密钥（`memoryLedger.ts` 构造器），这意味着 backend 重启后旧区块签名无法被新公钥验证。**接线时必须先解决**：密钥持久化到文件（`MEMORY_DIR/coordinator.key`），首次生成后复用。
3. **检索索引的同步**：BM25 索引是可重建的（`MemorySearchIndex.rebuild`），设备同步区块后需增量更新索引（`add`），或落后较多时 `rebuild`。
4. **secret 脱敏边界**：账本 append-only，`scrubSecrets` 必须在写入前剥离（backend 已做），设备侧只追加、不重新脱敏。
5. **设备存储目录**：设备本地账本用 `DEVICE_DATA_DIR` 下的子目录，与 backend 的 `MEMORY_DIR` 区分，避免路径冲突。

## 9. 与 agentmemory 的关系（可选的更优路径）

`rohitg00/agentmemory`（Apache-2.0）提供了更完整的记忆语义（四层整合、混合检索、多 agent 作用域、mesh sync）。本设计的「哈希链防篡改 + 中心广播同步」是**自研轻量版**；若后续要更强的记忆语义，可把 agentmemory 作为记忆层备选后端替换，其「租约/信号/mesh sync」与本文的 gossip 模型同构，迁移成本可控。
